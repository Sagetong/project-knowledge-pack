# 80 · 合并与继承策略

> 建立于 2026-10-07，由用户提出安全需求：
> **「我可以使用别的经验包，但合成之后底层框架依然是我默认的；
> 不是直接覆盖或消除，而是全部记录下来。」**

---

# 第一节 · 核心安全原则

## 一句话

> **别人的经验可以进来，别人的框架不可以进来。**

## 为什么

若合并时允许他人覆盖核心层，会产生三个风险：

| 风险 | 后果 |
|---|---|
| **作者成为攻击面** | 恶意者塞入污染核心，作者一发布就变成散播病毒的母体 |
| **责任无法界定** | 出事时无法判断是原作者的还是合并进来的 |
| **信任崩塌** | 没人敢用一份"来源不明的核心" |

**⇒ 因此：核心层默认使用【原作者版本】，绝不因合并而变更。**

---

# 第二节 · 三层继承规则

| 层 | 目录 | 合并时的行为 | 理由 |
|---|---|---|---|
| **核心层** | `core/`、`00-底层逻辑/`、`30-工具/` | ❌ **拒绝覆盖。保留原作者版本** | 安全底线 |
| **共享层** | `20-历史经验/data/universal/`、`40-Skills/universal/`、`10-说明书/` | ✅ **可自由合并** | 无副作用，越共享越强 |
| **贡献层** | `20-历史经验/data/contributed/`、`40-Skills/contributed/` | ✅ **只追加，署来源** | 保留归属 |
| **本地层** | `local/`、`STATE.md`、`LESSONS.md`、`50-环境档案/` | ❌ **不参与外发** | 含本机敏感信息 |
| **史书层** | `70-文明史书/` | ✅ **只追加** | 记录一切，不删改 |

# 第三节 · 合并流程（六步）

```
第 1 步 · 冻结基线
  对当前核心层全部文件计算 SHA256，写入 baseline-hashes.json

第 2 步 · 导入他人包（只读）
  解压到临时目录，绝不直接覆盖本地任何文件

第 3 步 · 分类
  逐文件判断属于：核心层 / 共享层 / 贡献层 / 本地层 / 史书层

第 4 步 · 核心层：比对并拒绝
  若他人包中含核心层文件：
    · 计算其哈希，与本地基线比对
    · 不同 → 拒绝导入，并记录到 merges/
    · 相同 → 跳过（无意义）
  ★ 核心层文件永不因合并而改变

第 5 步 · 共享与贡献层：合并
  · 共享层：按 id 去重后追加；同 id 不同内容则**两条都保留**并标注来源
  · 贡献层：只追加，每条必须带 contributor 字段
  · 绝不删除本地已有条目

第 6 步 · 写入史书
  产出 merges/merge-<时间>-<来源>.md，并向 chronicle.jsonl 追加一条
```

# 第四节 · 冲突处理（与"覆盖"的区别）

**遇到同一 id 有不同说法时，不允许二选一，必须两条都留：**

```json
{"id":"f042","claim":"系统代理会影响 AA","status":"falsified","source":"local"}
{"id":"f042","claim":"系统代理不影响 AA","status":"verified","source":"contributor-xxx","conflict_with":"local"}
```

**⇒ 后来者能看到"当时有两种说法，各自依据是什么"。**

**这与人类史书一致：不同史料并存，不强行统一。**

---

# 第五节 · 作者安全保证（对贡献者的声明）

**本经验包对外声明：**

1. **核心层由原作者维护并签名。** 任何第三方包的核心层变更都不会被采纳。
2. **合并只影响共享层与贡献层，且只追加不覆盖。**
3. **每次合并留痕**（`merges/` + `chronicle.jsonl`），可追溯到具体来源。
4. **原作者不对合并进来的共享内容作安全担保**，使用者应自行审阅。
5. **贡献者的内容会被署名保留**，不会被抹去来源。
