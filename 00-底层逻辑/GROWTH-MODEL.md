# Growth Model —— 这个包如何随时间变强

> **本文描述经验包的成长路径：从「一台电脑的记忆」到「AI 集体经验基础设施」。**
> 它回答一个核心问题：**为什么用得越久、参与的人越多，它越有价值？**

---

# 一、成长的四层

```
第 1 层  单机记忆          一台电脑、一个 AI
   ↓
第 2 层  多 AI 共享        同一台电脑上，多个 AI 读写同一份记忆
   ↓
第 3 层  跨机分享          打包复制给另一台电脑 / 另一个人
   ↓
第 4 层  集体汇聚          N 个使用者，各自贡献经验，汇聚成公共知识
```

**⇒ 目前处于第 1 层。脚手架已为第 2~4 层预留位置。**

---

# 二、每一层的机制

## 第 1 层：单机记忆（当前）

**机制**
```
AI 解决难题 → harvest.ps1 → 写入 local 命名空间
下次 AI    → memory.ps1 context → 读取
```

**产生的价值**：本机 AI 不再重复踩同一个坑。

**局限**：只对本机有效。

---

## 第 2 层：多 AI 共享

**机制**
```
GPT / Codex / DeepSeek / 其他 AI
        ↓ 都读同一个 AGENTS.md
        ↓ 都执行 memory.ps1 context
        ↓ 都执行 harvest.ps1 写回
      同一份记忆
```

**关键设计（已实现）**：
- `AGENTS.md` 是 AI 启动时必读的文件 → **写回规则的入口**
- `harvest.ps1` 是一条命令 → **降低写回成本**
- 格式统一 → **不同 AI 之间能互相读懂**

**⇒ 这一层的成败取决于「AI 是否主动写回」。**

**所以 `AGENTS.md` 里必须明确写**：
> *"解决了一个非平凡问题却不 harvest，下次还得重新踩。"*

---

## 第 3 层：跨机分享

**机制**
```
我的 experience-pack
        ↓ 复制 / 打包
别人的电脑
        ↓ 读 50-环境档案 了解差异
        ↓ 读 universal 命名空间（可迁移的知识）
        ↓ 忽略 local 命名空间（本机特有）
```

**关键设计（已预留）**：
- **命名空间分离**：`local` 不外传，`universal` 可分享
- **`origin` 字段**：标明每条经验的来源
- **`MANIFEST.json` + SHA256**：复制后能校验完整性
- **`50-环境档案`**：说明哪些是本机特有的

**⇒ 这一层需要「提升（promote）」机制：把 local 里抽象出的通用规律移到 universal。**

---

## 第 4 层：集体汇聚（目标形态）

**机制**
```
使用者 A 的 AI ──┐
使用者 B 的 AI ──┤
使用者 C 的 AI ──┼──→ 汇聚层（去重 / 校验 / 抽象）──→ universal 知识库
研究者 D       ──┤
其他人         ──┘
                        ↓
              下一批使用者的 AI 直接继承
```

**这一层还没实现，但脚手架已预留：**
- `contributed\` 命名空间 —— 外部经验的入口
- `origin` 字段 —— 区分来源
- `60-贡献协议\` 目录 —— 定义贡献流程
- `SCHEMA.md` 第七节 —— 保证不同版本能合并

---

# 三、为什么"越用越强"（正反馈）

```
经验越多
   ↓
新 AI 踩坑越少
   ↓
它能把精力放在真正新的问题上
   ↓
产出新的、更深入的经验
   ↓
经验质量提升
   ↓
吸引更多使用者
   ↓
（回到起点，但基数更大）
```

**⇒ 这是典型的网络效应：价值随参与者数量超线性增长。**

---

# 四、必须解决的四个难题

**愿景很好，但有四个硬问题。不解决，第 4 层就不会成立。**

## 难题 1：质量控制（噪声问题）

```
1000 条经验里，可能只有 50 条有价值
其余是：重复的、过于具体的、表述模糊的、错误的
```

**可能的解法**：
| 方法 | 说明 |
|---|---|
| **状态分级** | 已实现：`verified` 才可信 |
| **多来源交叉验证** | 同一结论被 N 个独立来源记录 → 提升可信度 |
| **使用反馈** | 一条经验被成功应用 M 次 → 提高权重 |
| **过期标记** | 长期未被引用的降权（`expires` 字段已预留） |

## 难题 2：信任与防投毒

```
恶意 AI 写入错误经验 → 后续所有使用者被污染
```

**可能的解法**：
| 方法 | 说明 |
|---|---|
| **`contributed` 隔离** | 外部经验不直接影响决策，先进入隔离区 |
| **提升需验证** | 只有经过实测的经验才能进 `universal` |
| **签名** | 贡献者签名（未实现，已预留位置） |
| **可追溯** | `origin` 字段能追溯到具体来源 |

## 难题 3：通用 vs 特异

```
"我的防火墙规则" 对你机器有效，对我无效
"网络问题先开日志" 对所有人都有效
```

**⇒ 这就是为什么必须有 `local` / `universal` 分离。**

**判定标准（建议）**：
```
一条经验若满足以下全部，才可提升为 universal：
  ① 不含具体路径 / IP / 主机名 / 凭据
  ② 描述的是「原理 / 模式」而不是「本机的一次操作」
  ③ 至少在一个不同环境下复现过（或理论必然）
```

## 难题 4：自动写回的触发

```
AI 不会"自动"做任何事
```

**⇒ 唯一有效的方式：把规则写进 AI 必读的文件。**

**已实现**：`AGENTS.md` 顶部的规则 + `FOR-AI.md` 的会话流程。

**⇒ 但"必读"本身依赖 AI 是否会读 `AGENTS.md`。**

**这是平台相关的**：
```
Codex            ✅ 自动读 AGENTS.md
Claude Code      ✅ 自动读 AGENTS.md / CLAUDE.md
DSH              ✅ 可配置
其他 AI          🟡 需要确认
```

**⇒ 所以本包的可用性，部分取决于目标 AI 平台是否支持"项目级指令文件"。**

# 五、成长的阶段目标

| 阶段 | 状态 | 标志 |
|---|---|---|
| **① 结构就位** | ✅ 已完成 | 目录、schema、工具、文档齐备 |
| **② 本机跑通** | 🟡 进行中 | 至少 50 条高质量 local 经验 |
| **③ 多 AI 共享** | ⬜ 待验证 | 两个以上 AI 实际读写同一份记忆 |
| **④ 提炼通用层** | ⬜ 待做 | `universal` 里有 10+ 条可迁移知识 |
| **⑤ 打包分享** | ⬜ 待做 | 另一台电脑能直接用起来 |
| **⑥ 开源** | ⬜ 用户设想 | 贡献协议、脱敏、签名就位 |
| **⑦ 集体汇聚** | ⬜ 远期 | 多来源经验自动合并 |

**⇒ 现在在②。不要把⑥⑦的复杂度提前引入。**

# 六、现在应该做什么 / 不该做什么

## ✅ 现在该做

```
① 用它 —— 每天解决的问题都 harvest 进去
② 积累量 —— 让 local 经验达到 50~100 条
③ 找通用性 —— 从中识别哪些可以提升为 universal
④ 验证多 AI 协作 —— 让 Codex 和 DeepSeek 都读写它
⑤ 发现问题 —— 记录下"用起来别扭的地方"，那是设计的改进点
```

## ❌ 现在不该做

```
① 不要现在就做去重/合并算法 —— 数据量不够，做了也没法验证
② 不要现在就设计贡献协议 —— 还没到分享阶段
③ 不要现在就搞签名/防投毒 —— 先把有用的积累起来
④ 不要为了"将来可能用到"而过度设计
⑤ 不要在只有 20 条经验时就抽象"通用规律" —— 样本太少
```

**⇒ 原则：脚手架预留到位，但功能按需实现。**

---

# 七、一个诚实的判断

> ## **这个想法有多大价值，取决于「有多少 AI 在多少场景下真的会主动写回」。**
>
> **技术框架我已经搭好了。真正决定成败的是：**
> ```
> ① 目标 AI 平台是否支持自动读取项目指令文件（AGENTS.md）
> ② 写回是否足够省事（现在是一条命令）
> ③ 积累的经验是否真的能被后续 AI 复用（需要验证）
> ```
>
> **⇒ 这三件事只能靠实际使用来验证，设计再多也没用。**

---

# 八、一句话

> ## **脚手架的目的是「让未来的增长不需要重构」。**
> ## **但增长本身，只能靠一条一条真实的经验堆出来。**
