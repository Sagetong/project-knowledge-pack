# 底层逻辑 —— 这套经验包为什么能运转

> 本文说明：经验包的**结构原理**、**各部分的依赖关系**、以及**为什么这样设计**。
> 读它，你就能理解为什么每个文件在那里，以及怎么扩展它。

---

# 一、要解决的问题

**根源问题**：
```
AI 的对话上下文会被压缩、会换新会话
        ↓
每次新会话/新 AI 接手，都要从零摸索
        ↓
用户被迫反复解释项目历史 = 用户又在当传话筒
```

**⇒ 所以需要一个外部的、持久的、可被任何 AI 读取的记忆载体。**

---

# 二、核心设计原则

| 原则 | 为什么 |
|---|---|
| **① 分层** | 不同用途的内容分开：「怎么写代码」和「上周做了什么」不该混在一起 |
| **② 双可读** | 同一份知识同时提供**人类可读**（Markdown）和**机器可读**（JSONL）两种形式 |
| **③ 只追加** | 历史永远保留，不覆盖。这样能追溯"当时为什么这么想" |
| **④ 状态分级** | 每条事实必须标注 verified/hypothesis/unverified/falsified |
| **⑤ 一条命令** | 任何操作都要能一条命令完成，否则 AI 不会主动做 |
| **⑥ 自包含** | 整个包可以整体复制走，不依赖外部路径 |

```

│
├─ 00-底层逻辑\  ← 本目录

│

│    ├─ AGENTS.md ················· 工作规范（AI 行为准则）
│    ├─ FOR-AI.md ················· 给 AI 的完整使用指南
│    └─ FOR-HUMAN.md ·············· 给人看的说明
│
├─ 20-历史经验\  ← "发生过什么"
│    ├─ STATE.md ·················· 当前状态（人类可读）
│    ├─ LESSONS.md ················ 经验教训（人类可读）
│    ├─ HANDOFF-早期.md ············ 项目早期交接文档
│    └─ data\ ····················· ★ 机器可读层

│         ├─ lessons.jsonl ········ 经验库
│         ├─ timeline.jsonl ······· 时间线
│         ├─ decisions.jsonl ······ 决策库

│         └─ README.md ············ data 层说明
│

│    ├─ memory.ps1 ················ 查询 / 追加 / 生成简报

├─ 40-Skills\    ← "会做什么"（可执行的知识）

     └─ (环境特有的知识、坑、路径)
```

# 四、数据流（核心机制）

## 4.1 读取流（AI 接手时）

```
新 AI 启动
   ↓
读 10-说明书\AGENTS.md          ← 看到"先读 STATE/LESSONS"的指引
   ↓
读 20-历史经验\STATE.md          ← 知道现在到哪
   ↓
执行 30-工具\memory.ps1 context  ← ★ 拿到结构化简报
   ↓
（同时生成 memory\CONTEXT.md）
   ↓
完整上下文就绪，可以开始工作
```

**为什么要有 `context` 这一步？**

因为 JSONL 是给机器看的，AI 要读完 4 个文件再自己拼接。`context` 命令把这件事**一次做完**，输出一份可直接使用的简报。

## 4.2 写入流（AI 学到新东西时）

```
AI 解决了一个非平凡问题
   ↓
执行 30-工具\harvest.ps1 \
     -Title "..." -Problem "..." -Solution "..." -Reusable "..." \
     -MakeSkill -SkillName "..." -SkillWhen "..." -SkillSteps "..."
   ↓
   ① 追加到 20-历史经验\data\lessons.jsonl
   ② 追加到 20-历史经验\data\timeline.jsonl
   ③ 生成 40-Skills\<name>\SKILL.md
   ④ 更新 20-历史经验\data\index.json
   ↓
下次任何 AI 执行 context 就能看到
```

**⇒ 这就是"自动经验总结 + Skill 保存"的实现。**

**为什么必须是一条命令？**

因为如果需要 AI 手动编辑 4 个文件，它**不会主动做**。降低操作成本 = 提高积累概率。

# 五、为什么用 JSONL 而不是其他格式

| 格式 | 追加安全 | 机器可解析 | 人可读 | 并发安全 | 结论 |
|---|---|---|---|---|---|
| **JSONL** | ✅ 加一行 | ✅ | ✅ | ✅ | ★ 选用 |
| 单个 JSON | ❌ 要重写整个文件 | ✅ | 🟡 | ❌ | ❌ |
| Markdown | ✅ | ❌ | ✅ | 🟡 | 用作人类层 |
| SQLite | ✅ | ✅ | ❌ | ✅ | ❌ 需要驱动，跨 AI 麻烦 |
| YAML | 🟡 | ✅ | ✅ | ❌ | 🟡 缩进敏感，易错 |

**⇒ JSONL 是唯一同时满足全部四项的格式。**

# 六、状态分级为什么重要

**这是防止"把假设当事实"的机制。**

```
verified    ✅ 有证据       → 可以作为决策依据
hypothesis  ⚠️ 合理推断     → ❌ 不可以
unverified  ❓ 待实测       → ❌ 不可以
falsified   ❌ 已证伪       → ❌ 不要再提
```

**真实案例（本项目的）：**

| 事实 | 当时的标记 | 后来 |
|---|---|---|
| "阿里云 IP 会被 OpenAI 封" | ⚠️ hypothesis | **实测证伪** → 标为 falsified |
| "Free 账号有 Site Tools 权限" | ❓ unverified | 至今未验证 |
| "Reality dest 用 microsoft.com 没问题" | ⚠️ hypothesis | **实测证伪** → 写进 lessons |

**⇒ 如果不分级，这些假设会被后续 AI 当成事实继承下去，导致错误决策。**

# 七、Skill 与 Lesson 的区别

```
Lesson（经验）= "我踩过这个坑，原因是……"       ← 知识（知道）
Skill（技能）  = "遇到这个情况，按这 3 步做"     ← 行动（会做）
```

**一条经验可以派生出多个 Skill；一个 Skill 可能综合多条经验。**

**⇒ 所以两者分开存放，但用 id 互相引用。**

# 八、扩展方式

## 加一个新的知识类别

```
① 在 20-历史经验\data\ 下新建 <name>.jsonl
② 在 data\index.json 的 schema 和 stats 里登记
③ 在 30-工具\memory.ps1 里加对应的 Cmd-<Name> 函数
④ 在 memory.ps1 的 switch 里注册命令
```

## 加一个新的工具

```
放在 30-工具\ 下即可。
约定：脚本用 $PSScriptRoot 定位包根目录，不要硬编码路径。
```

## 迁移到另一台电脑

```
① 整个 experience-pack 文件夹复制过去
② 检查 50-环境档案\ 里的路径是否仍然有效
③ 若不同，新建一份环境档案而不是改旧的
```

# 九、已知限制

| 限制 | 说明 | 可能的改进 |
|---|---|---|
| **依赖 PowerShell** | 非 Windows 环境需要改写工具 | 可加 bash 版本 |
| **无版本控制** | 没有 git 历史（但 JSONL 是只追加的，近似有时间线） | 未来可加 git |
| **检索是全文匹配** | `search` 用简单字符串匹配，无索引 | 数据量大时可加标签索引 |
| **无去重** | 同一条经验可能被记录两次 | 可加相似度检查 |
| **AI 不会自动调用** | 需要 AGENTS.md 里写明规则 | 已写入规范 |

# 十、一句话总结

> ## **这套东西的本质：把「AI 脑子里的临时上下文」变成「磁盘上持久的、任何 AI 都能读的结构化知识」。**
>
> **核心机制只有两个：**
> ```
> 读：memory.ps1 context   → 拿到全部记忆
> 写：harvest.ps1 ...      → 固化新经验 + 生成 Skill
> ```
>
> **其他所有文件都是为了这两条命令服务的。**
