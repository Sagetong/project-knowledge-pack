# 91 · 虎符 v3 · 双口令（Two-Key）体系

> 建立于 2026-10-07，由用户提出：
> **「两条验证方法要一起验证：一条你（AI）生成，一条我自己设。
> 我会人为保存两条，即使你被黑客攻击也不会造成泄露。」**
>
> **→ 这在密码学上叫「双人规则 / 双重控制」（two-person rule / dual control）：
> 任何一方单独都无法解锁。**

---

# 第一节 · 为什么双击比单密码强

## 单密码的弱点

| 场景 | 后果 |
|---|---|
| AI 被入侵 | 若密码在 AI 手里 → 直接失守 |
| 笔记本被偷 | 若密码只在本子上 → 直接失守 |
| 口令复用 | 一处泄露，处处失守 |

## 双口令的优势

```
左符（AI 生成）  ─┐
                 ├─→ 两半必须同时正确 → 才能派生出解密密钥
右符（用户设定）  ─┘
```

| 攻击场景 | 结果 |
|---|---|
| **AI 被完全入侵** | 攻击者拿到左符，但**不知道右符** → ❌ 打不开 |
| **笔记本被偷** | 窃贼拿到右符，但**不知道左符** → ❌ 打不开 |
| **两处都被拿到** | 失守 —— **所以必须分开保存** |

**⇒ 安全性不取决于「密码多复杂」，而取决于「秘密是否分散在两处」。**

---

# 第二节 · 一个必须诚实说明的技术细节

## 问题

**AI 输出的任何内容都会进入会话记录文件。** 所以「AI 生成的口令」对 AI 并非绝对不可见。

## 为什么这仍然可以接受

1. **真正的秘密是右符。** 右符由用户设定，**AI 从未见过、不落任何文件**。
2. **两半必须同时正确。** 只知左符毫无用处。
3. **左符可轮换。** 一旦怀疑泄露，重新生成左符即可，右符不动。

## 因此的设计定位

| 符 | 角色 | 如果泄露 |
|---|---|---|
| **左符** | **门槛 / 盐** | 降低安全性但不致命，可轮换 |
| **右符** | **真正的秘密** | 致命，必须严格保护 |

**⇒ 一句话：左符是"第一道门"，右符是"保险柜钥匙"。门被撬开不等于保险柜被打开。**

# 第三节 · 密钥派生流程

```
输入：
  左符（32 字符，AI 生成，用户抄写）
  右符（用户自设，AI 未知）
  盐  （32 字节随机，存于 dual-key-salt.bin）

派生：
  masterKey = PBKDF2-HMAC-SHA256(
                  password = 左符 + "|" + 右符,
                  salt     = 盐,
                  iterations = 600000,
                  dkLen    = 32 字节
              )

用途：
  masterKey → AES-256-CBC 加密「底层隐私设置」
```

## 为什么用 PBKDF2 而不是简单拼接

| 简单拼接的问题 | PBKDF2 的解决 |
|---|---|
| 拼接后直接当密钥 → 可被快速爆破 | **60 万次迭代 → 每次尝试都极慢** |
| 无法防彩虹表 | **加盐 → 同一口令也产生不同密钥** |
| 口令长度不一 | **固定输出 32 字节** |

# 第四节 · 如何验证口令正确而不存口令

## 问题

不能存口令，那怎么判断用户输对了？

## 解法：验证块（verification blob）

```
初始化时：
  已知明文 PLAINTEXT = "TIGER-TALLY-DUAL-KEY-V1"
  blob = AES-Encrypt(masterKey, PLAINTEXT)
  把 blob 存在文件里

解锁时：
  用输入的左右符派生出 candidateKey
  尝试解密 blob
    → 得到 PLAINTEXT  = 两符都正确 ✅
    → 解密失败/乱码   = 至少一个错了 ❌
```

**⇒ 文件里只有密文，没有任何口令信息。暴力破解需要同时猜中两个口令，成本极高。**

| 文件 | 内容 | 是否含秘密 |
|---|---|---|
| `dual-key-salt.bin` | 32 字节随机盐 | ❌ 盐不是秘密，可公开 |
| `dual-key-meta.json` | 左符指纹、算法参数、时间 | ❌ 只有指纹（不可逆） |

| **左符** | —— | ✅ **只在用户手上** |
| **右符** | —— | ✅ **只在用户手上** |

**⇒ 三个文件加起来也推不出任何口令。**

# 第六节 · 操作纪律（关键）

## 必须做的

| # | 要求 |
|---|---|
| 1 | **左符与右符分开保存**（不同本子 / 不同设备 / 一个纸质一个手机） |
| 2 | 左右符都要手抄，不要只存电子版 |
| 3 | 右符不要用任何已有密码，不要复用 |
| 4 | 定期核对左符指纹 `D0A997CBA6E33F9A` 确认抄写无误 |
| 5 | 怀疑左符泄露 → 立即轮换左符（右符不动） |

## 绝对不能做的

| # | 禁止 |
|---|---|
| 1 | ❌ 左右符存在同一处 |
| 2 | ❌ 把任一口令写进经验包目录内的任何文件 |
| 3 | ❌ 把任一口令提交到 Git |
| 4 | ❌ 把左右符一起拍照存在同一台设备 |
| 5 | ❌ 使用口语化、有规律的右符（如生日、名字） |

# 第八节 · 加在设计上的两条新铁律

## 铁律 1 · 秘密必须分散

**任何一个单一位置泄露，都不得导致全盘失守。**

这是本体系存在的全部理由。

## 铁律 2 · 可轮换优先

**左符可以换，右符不动。** 因为左符的暴露面更大（经过 AI 环境）。
**⇒ 优先选择"可轮换的秘密"承担暴露风险，让"不可轮换的秘密"深藏。**

---

# 第九节 · 与虎符 v2 的关系

| 体系 | 保护对象 | 手段 |
|---|---|---|
| **v2（签名）** | **对外**：证明核心出自作者 | Ed25519 私钥签名 |
| **v3（双口令）** | **对内**：保护本地隐私层 | 双口令派生密钥加密 |

**⇒ 两者互补，不重叠：**
- v2 防的是"别人冒充我发布"
- v3 防的是"别人偷看我的隐私"

**⇒ 合起来才是一副完整的虎符：对外可验来源，对内可守秘密。**
