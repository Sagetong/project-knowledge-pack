# 90 · 虎符 v2 · 作者签名体系

> 建立于 2026-10-07，由用户提出安全需求并确认作者身份为 **Sage Tong**。
> **核心结论先说：名字是【公开的身份】，不是【密钥】。名字公开对安全零影响。**

---

# 第一节 · 先纠正一个常见误解

## 用户的顾虑

> 「我这个开源作者的标志或名字，是否要公开也不一定……但只是这个的话并不保险，
> 因为后面我原作者的名字是可能会公开的。」

## 答案

**名字公开不公开，与安全性【完全无关】。原因：**

| 攻击者要伪造的 | 不是 | 而是 |
|---|---|---|
| 伪造一份"看起来像你发布的包" | ❌ 不是你的名字 | ✅ **你的签名** |

**名字是公开标识（identity），不承担任何保密职责。**
**安全来自密钥对 —— 私钥签名，公钥验签。**

**⇒ 这正是虎符的本意：一半在君、一半在将，合符才生效。**
**⇒ 名字对不上没关系，符对不上才致命。**

# 第二节 · 虎符的两半

## 现有的一半（已实现 ✅）

**对称加密** —— 保护 `local/` 隐私层：

| 工具 | 用到的算法 |
|---|---|
| `tally-lib.ps1` | SHA256, AES, RNGCryptoServiceProvider, HMAC, Rfc2898(PBKDF2) |
| `lock.ps1` | SHA256, AES, RNGCryptoServiceProvider, HMAC |
| `init-tally.ps1` | SHA256, AES, HMAC |
| `verify-tally.ps1` | SHA256 |

**⇒ 这一半做的是"上锁"，防的是"别人看我的隐私数据"。**

## 缺失的一半（v2 补齐 ★）

**非对称签名** —— 证明"核心确实出自作者"：

| 现在有什么 | 缺什么 |
|---|---|
| `baseline-hashes.json` 里 17 个文件的 SHA256 | **签名** |

**⇒ SHA256 只能验【完整性】（文件有没有被改坏），**
**⇒ 不能验【来源】（这份核心到底是不是 Sage Tong 发的）。**

**这是当前最大的安全缺口。**

# 第三节 · 虎符 v2 设计

## 三层保护，对应古代虎符的三个层次

```
┌─────────────────────────────────────────────────────────┐
│  左符 · 作者私钥（Sage Tong 独占，离线保存）              │
│  · 算法: Ed25519                                        │
│  · 用途: 对核心清单签名                                  │
│  · 存放: 离线，绝不进仓库                                 │
│  · 口令: 强烈建议设置                                    │
└───────────────────────┬─────────────────────────────────┘
                        │ 签名
                        ▼
┌─────────────────────────────────────────────────────────┐
│  核心清单 + 签名文件（随包发布）                          │
│  · core-manifest.txt    17 个核心文件的路径与哈希         │
│  · core-manifest.txt.sig  作者签名                       │
└───────────────────────┬─────────────────────────────────┘
                        │
                        ▼
┌─────────────────────────────────────────────────────────┐
│  右符 · 作者公钥（公开发布，人人可验）                    │
│  · 文件: allowed_signers                                │
│  · 身份串: tally-author@SageTong                        │
│  · 用途: 任何使用者一条命令即可验证                       │
└─────────────────────────────────────────────────────────┘
```

## 合符（验证动作）

```powershell
ssh-keygen -Y verify -f allowed_signers -I tally-author@SageTong `
           -n file -s core-manifest.txt.sig < core-manifest.txt
```

**通过 → 核心确实出自 Sage Tong，未被篡改。**
**不通过 → 要么被改过，要么根本不是他发的。二者都要拒绝。**

# 第五节 · 私钥管理铁律（最重要）

| 铁律 | 说明 |
|---|---|
| **R1. 私钥绝不进仓库** | 任何情况下都不得提交到 Git。要写进 `.gitignore` |
| **R2. 私钥与包物理分离** | 与 `core/security.json` 里"密钥文件必须与加密文件物理分离存放"一致 |
| **R3. 私钥设口令** | 测试时用了空口令是为了验证机制；**正式使用必须设口令** |
| **R4. 私钥离线备份** | 至少两份离线介质（U 盘/纸质助记词），丢失即无法再签新版本 |
| **R5. 公钥可随意公开** | 它就是给人验签用的，贴官网、贴 README 都行 |

## 私钥泄露的后果

**若私钥泄露，攻击者可以签出"看起来完全合法"的核心 → 使用者无法分辨。**
**这是唯一真正需要严防的东西 —— 名字泄不泄露无所谓。**

# 第七节 · 回答"名字要不要公开"

## 结论：**公开，而且应该公开。**

| 理由 | 说明 |
|---|---|
| **名字不承担安全职责** | 安全由密钥承担，与名字无关 |
| **公开名字建立信任** | 开源项目需要可追责的作者身份 |
| **不公开反而可疑** | 匿名核心 + 要求别人信任 = 不合理 |
| **古代虎符同理** | 符上刻谁的名字不重要，重要的是符对不对得上 |

**⇒ 所以：名字公开 + 私钥严格保密，这才是正确的组合。**

**⇒ 把名字当作虎符的一部分是可以的（刻在符上），但不要指望它提供安全。**
